### 1.1 官方语法行（逐字抄）

```
sort [/r] [/+<N>] [/m <kilobytes>] [/l <locale>] [/rec <characters>]
     [[<drive1>:][<path1>]<filename1>] [/t [<drive2>:][<path2>]] [/o [<drive3>:][<path3>]<filename3>]
```

`#parameters` 表共 10 项：`/r`、`/+<N>`、`/m <kilobytes>`、`/l <locale>`、`/rec <characters>`、
`filename1`、`/t`、`/o`、**`/unique`**、`/?`。

### 1.2 与官方文档对不上的地方（如实记录）

| # | 现象 | 处理 |
|---|---|---|
| a | **本机 `sort /?` 完全没有列 `/unique`**（2196 字节里搜不到 `uniq`），但官方 `#parameters` 有它，且**本机实测 `/unique` 与 `/uniq` 都能用**（`list.txt` 6 行 → 3 行，退出码 0）。 | **收录**，并在该动作的 `sources` 里写明"出处只有官方页一侧"。这正是 playbook §10 第 32 条（本机 `/?` 也是官方文档，但必须标注出处范围）的方向。 |

| d | 官方页**没有 exit codes 小节**（`fc` 那一页有）。 | 只写本机实测到的 0 与 1 两条，**不编造码表**（R1）。 |

## 3. ★ 本包最重要的一条：裸 `sort` 在宿主手里是"静默无输出" ★

### 3.1 实测证据（这是任务点名要先量清的前置问题）

宿主的执行模型是 **CreateProcess + 重定向 stdout/stderr + 立刻 `StandardInput.Close()`**。
把 `sort.exe` 直接按这个模型跑，三种输入形态的结果是：

| # | argv | stdout | stderr | 退出码 | 结论 |
|---|---|---|---|---|---|
| 1 | `sort.exe`（无参数） | **0 字节** | **0 字节** | **0** | ⚠ **"成功"却什么都没排** |
| 2 | `sort.exe /R`（无输入文件） | **0 字节** | **0 字节** | **0** | ⚠ 同上 |
| 3 | `sort.exe <文件>` | 46 字节（排好的行） | 0 字节 | 0 | ✔ 正常 |

原因很清楚：官方文档 `filename1` 一栏原文是
**"If no file name is specified, the standard input is sorted"**，
Remarks 又写 "you can first use the sort command with no parameters … press CTRL+Z"。
也就是说**裸 `sort` 是设计给人手敲的**：它等你在键盘上输入、用 Ctrl+Z 结束。
宿主把 stdin 一关，它立刻拿到 EOF，读到 0 行，于是"成功地"输出了 0 行 ——
**没有报错、退出码 0、连一句提示都没有**。这是最坏的一类失败：看起来跑成功了。

### 3.2 我采用的写法，以及为什么不用其它写法

**采用：把输入文件作为位置参数直接交给 sort.exe（官方语法里的 `filename1`）。**

```yaml
locate:
  executable: sort.exe          # 直接起 sort.exe，不经 cmd
actions:
  - id: sort-asc
    command: ""
    fields:
      - id: inputFile           # 位置参数，required: true
        type: file
        style: positional
```

理由有三条：

1. **它出自官方语法行**，而且是官方**推荐**的那条路 —— `filename1` 一栏原文：
   "Specifying the input file is faster than redirecting the same file as standard input"。
2. **它不需要 stdin**：`sort.exe <文件>` 走的是文件路径，与宿主关不关 stdin 无关（§3.1 第 3 行实测）。
3. **命令行最干净**：用户看到的预览就是 `sort.exe C:\data\names.txt`，
   符合 R6"把命令摆明白"的目的；不用解释"为什么前面套了一层 cmd"。

**同时实测过、也能工作、但最终没采用的写法**（留给后来者，免得重新摸索）：

| 写法 | argv（宿主会把整串当参数交给 cmd） | 实测结果 | 为什么不采用 |
|---|---|---|---|
| `cmd /c type <文件> \| sort` | `locate.executable: cmd.exe` + `command: /c` + `commandArgs: ["type", …, "\|", "sort"]` | **可用**：46 字节正确输出，退出码 0 | 多一层 cmd（进程、退出码、错误信息都变成 cmd 转述的），命令行预览变难读；而官方本来就支持直接给文件名，没必要绕 |
| `cmd /c sort < <文件>` | `command: /c` + `commandArgs: ["sort", "<", 文件]` | **可用**：46 字节正确输出，退出码 0 | 同上，而且 `<` 重定向写在字段里会让参数看起来像路径 |

**"裸 sort"（不给文件名）明确不可行**，所以本清单**每一个动作都把「要排序的文件」设为
`required: true`** —— 这不是普通的必填校验，而是**为了让界面不可能生成那条静默失败的命令**。
`sort /O <文件>` 那种"输出到文件"的形态也一并排除了（见 §6）。

### 3.3 一个必须写清的连带发现：`sort` 会**创建**输出文件

| argv | stdout | 结果 |
|---|---|---|
| `sort.exe /O %TEMP%\…\sorted-out.txt <文件>` | 0 字节 | `sorted-out.txt` **被创建**，46 字节（排序结果写进了文件） |
| `sort.exe /O %TEMP%\…\empty-out.txt`（**无输入文件**，stdin 被关） | 0 字节 | `empty-out.txt` **被创建，0 字节** |

也就是说 `/O` 是一条会**写文件**的路径，即使输入是空的也会把文件建出来。
本包承诺"只做只读动作"，因此 **`/O` 不收录**（见 §6）。这一条同时说明：
**"sort 是只读的"这个说法只在"不给 `/O`"的前提下成立**，NOTES 里必须点明。

## 4. 编码：**OEM 代码页（本机 936，即 GBK）**，不是 UTF-8（实测原始字节，R7）

判编码必须用带中文的输出。本机 `sort` 的输出天然带中文（中文帮助、中文错误消息），
另外还造了含中文内容与中文文件名的样本。用 `.NET Process` + `BaseStream` 拿**原始字节**：

| 场景 | 长度 | 首字节片段 | 严格 UTF-8 解码 | 结论 |
|---|---|---|---|---|
| `sort names.txt`（含 `中文字` 一行） | 46 B | `… 63 68 65 72 72 79 0d 0a **d6 d0 ce c4 d7 d6** 0d 0a` | **抛异常**（`Unable to translate bytes [D6] at index 38`） | `d6 d0 ce c4 d7 d6` = **GBK 的「中文字」** → 不是 UTF-8 |
| `sort <中文文件甲.txt>`（内容含中文） | 23 B | `bc d7 d0 d0 20 c4 da c8 dd 0d 0a …` | **抛异常** | 同上，GBK |
| `sort /?`（中文帮助） | 2196 B | `53 4f 52 54 20 5b 2f 52 5d …`（ASCII 头）+ 大量 GBK 汉字 | **抛异常** | 帮助是**中文**且是 GBK |
| `sort nope.txt`（错误消息，**写 stderr**） | 81 B（stderr） | `… 5c 6e 6f 70 65 2e 74 78 74 **cf b5 cd b3 d5 d2 b2 bb b5 bd** …` | **抛异常** | `cf b5 cd b3…` = GBK 的「系统找不到…」 |
| `/M` 的警告消息 | 51 B（stderr） | GBK 汉字 | — | 同上 |

判定依据三条（都指向同一个结论）：

1. **严格 UTF-8 解码对每一份带中文的输出都抛异常** —— 用
   `new UTF8Encoding(false, /*throwOnInvalidBytes*/ true)` 解 `d6 d0 ce c4 d7 d6`，
   报 `Unable to translate bytes [D6] at index 38 from the specified code page to Unicode`。
2. **"高字节为 0 的比例"是 0%**（不是 UTF-16LE；UTF-16LE 的阈值判定见
   `windows-commands.md` §5.1）。
3. 用 `Encoding.GetEncoding(936)` 解码，得到完全通顺的中文
   （`apple / Apple / Banana / banana / cherry / 中文字`），
   而用 UTF-8 解码得到 `�������`。

所以 `runtime.encoding: **oem**`（宿主把 `oem` 解析成
`CultureInfo.CurrentCulture.TextInfo.OEMCodePage`，本机 = 936）。
写 `oem` 而不是写死 `gbk` 的理由：换成英文 Windows（437）或日文 Windows（932）时同一份清单仍然正确。

**这一条还有一个必须说清的边界**：以上证据都取自**宿主那种"无控制台"的条件**（§4.1 会看到，
`sort` 在有控制台时会退回英文）。但即使退回英文（纯 ASCII，3683 字节、`nonAscii = 0`），
用 936 解码也是逐字节正确的 —— 也就是说 `encoding: oem` 在两种条件下都对，
**这个选择不依赖"语言会不会变"这个未定因素**。

### 4.1 "有没有控制台"对 sort 的影响（与 `windows-commands.md` §5.3 的 route 现象对照）

**这是本包第二次修正的一条**（第一版只对比了"中文/中文"，没量到下面第三行）：

| 条件 | `sort /?` 输出 | 字节数 | 语言 |
|---|---|---|---|
| **无控制台**（`CreateNoWindow=true` + 重定向/管道）—— **这就是宿主形态** | `SORT [/R] [/+n] …` + 大量 GBK 汉字 | **2196** | **中文** |
| 有控制台，输出走**管道** | 同上 | 2196（管道里的原始字节） | **中文** |
| **有控制台**，输出**重定向到文件** | `SORT [/R] [/+n] …` 全 ASCII | **3683** | **英文**（`nonAscii = 0`） |

也就是说：**在宿主那种"没有控制台"的条件下，`sort` 一定输出中文 + GBK**（这是本包编码判定的实际依据）；
换成"有控制台 + 重定向到文件"时它会退回英文资源。
`windows-commands.md` §5.3 记的 `route` 是同一个现象（无控制台 → 退回英文），
**这里的方向是反的**（无控制台 → 中文），所以再次印证那条结论：
**"语言会不会变、往哪个方向变"必须逐命令实测，不能按命令族推断。**

对本包的实际影响是**两条**：

1. **编码**：宿主形态下输出是中文、字节是 GBK（§4 的证据就是在这个条件下抓的）；
   即使换成有控制台的英文输出（纯 ASCII），`oem`/936 解码同样正确 —— 所以 `encoding: oem` 两种条件下都成立。
2. **文案绝不能拿来判成败**：同一份失败（例如输入文件不存在）在有/无控制台时可能是中文、也可能变英文，
   所以本包一律用**退出码**判定，不看提示文字。

顺带一个对照：同批的 `fc.exe` 在**两种条件下都是"有控制台 = 英文"**（`/Z` 的报错、`/?` 的帮助都是），
只有"无控制台"才变中文 —— 见 `plugins/fc/NOTES.md` §4.1。**两个包的方向不一样。**

### 4.2 输出流：结果与帮助都在 stdout，错误都在 stderr

| 内容 | 流 |
|---|---|
| 排序结果 | stdout |
| `/?` 帮助（2196 B） | **stdout**（stderr 0 字节） |
| `无效命令行开关。` / `<路径>系统找不到指定的文件。` / `记录数量最多不得超过 65535。` / `无效的区域设置。` / `文件名、目录名或卷标语法不正确。` | **stderr**（stdout 0 字节） |
| `/M 100` 的 `警告: 该指定的内存大小过低，将被调整到最低值。` | **stderr**，**但退出码仍是 0**（警告不影响成功） |

## 5. 真机冒烟测试（R4，2026-10-01）

测试目录：`%TEMP%\fc-sort-probe`（**所有操作都在这里，没有碰任何用户数据**）。
夹具全部用 GBK 写入（模拟本机 ANSI 文本文件）：`names.txt`（6 行含中文）、
`list.txt`（6 行含 3 组大小写重复）、`a.txt` / `b.txt`（内容差在大小写）、
`tab-a.txt` / `tab-b.txt`（只差空白）、`中文甲.txt` / `中文乙.txt`（中文文件名）。

**冒烟脚本**：48 条用例，逐条用与宿主相同的模型（`CreateNoWindow=true` + 重定向 + 立刻关 stdin）
起进程，比对期望退出码。**结果 48/48 通过（失败 0 条）**。

### 5.1 清单里 6 条 examples 的忠实复跑

| # | 动作 | argv | 退出码 | 期望值 |
|---|---|---|---|---|
| 1 | version | `/?` | **0** | 0 ✔ |
| 2 | sort-asc | `names.txt` | 0 | 0 ✔ |
| 3 | sort-asc | `/+3 names.txt` | 0 | 0 ✔ |
| 4 | sort-desc | `/R names.txt` | 0 | 0 ✔ |
| 5 | sort-unique | `/UNIQUE list.txt` | 0 | 0 ✔ |
| 6 | sort-unique | `/UNIQUE /R list.txt` | 0 | 0 ✔ |

产物复核：`names.txt` 排序后 6 行 → 输出仍是 6 行（46 字节），顺序为
`apple / Apple / Banana / banana / cherry / 中文字`（**大小写不敏感**，与官方 Remarks 一致；
`apple` 与 `Apple` 的先后等于它们原文件里的出现顺序 → 稳定排序）。
`list.txt` 加 `/UNIQUE` 后 6 行 → **3 行**（`apple / Fig / pear`，大小写不同也算重复，
留下的写法是第一次出现的那一个）；再加 `/R` → `pear / Fig / Apple`。

### 5.2 字段风格：逐个开关把"紧贴"与"分开"都试一遍（playbook §9）

| 开关 | 官方写法 | 紧贴 | 两 token | 冒号 | 结论（本包采用） |
|---|---|---|---|---|---|
| `/R` | 无值 | — | — | — | `style: flag`，`prefix: "/R"` |
| `/UNIQUE` | 无值 | — | — | — | `style: flag`，`prefix: "/UNIQUE"` |
| `/+<N>` | 值紧贴 | `/+3` → **exit 0，真的从第 3 列起比较**（`apple…` 的排序结果与默认不同） | `/+ 3` → **exit 1**，`排序位置必须大于零。` | 未试（官方无冒号写法） | **`attached`** + `prefix: "/+"` |
| `/L <locale>` | 值分开 | `/LC` → **exit 1**，`无效命令行开关。` | `/L C` → **exit 0**；`/LOCALE C` → **exit 0** | `/L:C` → **exit 1** | **只有"两 token"能用**，且值只能是 `C` → 做成一个固定 flag：`prefix: "/LOCALE C"`（一个 host token，展开成两个 argv） |
| `/M <kilobytes>` | 值分开 | `/M1024` → **exit 1** | `/M 1024` → **exit 0** | `/M:1024` → **exit 1** | 只有两 token 能用 →（未做成字段，见 §6） |
| `/REC <characters>` | 值分开 | `/REC4096` → **exit 1** | `/REC 4096` → **exit 0** | `/REC:4096` → **exit 1** | 只有两 token 能用 →（未做成字段，见 §6） |
| `/T [path]` | 值分开 | — | `/T %TEMP%\fc-sort-probe names.txt` → **exit 0** | — | 只有两 token 能用 →（未做成字段，见 §6） |

**这就是本包唯一一处"必须实测才知道"的风格结论**：`sort` 的开关**分两类** ——
`/+n` 必须**紧贴**，`/L` `/M` `/REC` `/T` 必须**分开**。
按"看起来像哪一类"选必然踩一个坑（校验器查不出来，开关名和出处都是对的）。

### 5.3 退出码：含失败路径的逐条实测

| argv | 退出码 | stderr |
|---|---|---|
| `<文件>` | 0 | — |
| `/R <文件>` | 0 | — |
| `/?` | **0** | — |
| （无参数，stdin 被关） | **0** | — ← 见 §3.1，这是本包最危险的一条 |
| `/M 100 <文件>` | 0 | `警告: 该指定的内存大小过低，将被调整到最低值。` |
| `<不存在的文件>` | **1** | `<路径>系统找不到指定的文件。` |
| `/Z <文件>`（非法开关） | **1** | `无效命令行开关。` |
| `/L zh-CN <文件>` | **1** | `无效的区域设置。` |
| `/REC 99999 <文件>` | **1** | `记录数量最多不得超过 65535。` |
| `/+ 3 <文件>` | **1** | `排序位置必须大于零。` |
| `*.txt`（通配符） | **1** | `文件名、目录名或卷标语法不正确。` ← **sort 不接受通配符**，要自己逐个文件排 |

`exitCodes` 就按 0 / 1 两条写（官方页没有码表，见 §1.2d）。
`/?` 退出码 0 这件事与 `ipconfig`(1) / `chkdsk`(3) / `robocopy`(16) 那批都不同，
**又一次说明"各命令的 `/?` 退出码互不相同"，只能逐个实测**。

### 5.4 没冒烟的动作

**没有"完全没跑"的动作** —— 4 个动作的 examples 全部实跑过。但有三条限定必须说清：

1. **冒烟是在宿主之外**用 `.NET Process` 直接拼 argv 跑的（本次不能改宿主、也不该启动 GUI）。
   宿主链路（表单 → `ArgvBuilder` → `ProcessRunner`）**没有**跑 sort。
   不过本包的字段形状极简（`positional` 必填 + `flag` + `attached`），
   与已验证的 `robocopy` / `tar` 包同类，且 `ArgvBuilder` 的展开规则与 §5.1 用的 argv 一致。
2. `sort-unique` 的 `/unique` **在中文 Windows 的 `sort /?` 里查不到**（§1.2a），
   所以它的"出处只有官方页一侧"；本机实测只验证了"能用 + 真的去重"，
   没有验证它与 `/r`、`/m` 的交互边界（只试过 `/UNIQUE /R` 一起给 → exit 0）。
3. **大文件、多趟排序（跑满内存后落临时文件）这条路径没有构造** ——
   `/m` 与 `/t` 的语义按官方原文写，本包也没把它们做成字段（§6）。
   也就是说本包没有实测过"数据装不下内存时"的行为。

## 6. 故意没做的部分（给后来者的地图）

| 没做 | 原因 |
|---|---|
| **`/O [<drive3>:][<path3>]<filename3>`** | 官方有、实测可用，但它**会创建/覆盖一个文件**（§3.3 实测，连空输入都会建出 0 字节文件）。本包承诺只做只读动作，所以不收录。需要"把排序结果存成文件"的用户，可以自己把输出区的内容复制走，或者用命令行。**这是本包唯一一处"官方有、能力真实、但按只读约定主动放弃"的功能**，写在这里以免被当成遗漏。 |
| `/M <kilobytes>`（内存用量） | 官方有、实测可用（两 token 写法）。但它是纯性能调优：默认值官方自己说是"通常最佳"，改小了只会更慢、还有"警告 + 调整到最低值"的噪声（实测）。做成字段收益为负。 |
| `/REC <characters>`（记录最大字符数） | 官方有、默认 4096、上限 65535。只有行长超过 4 KB 的文件才用得上（本工具包的目标场景是名单/日志/hosts），留给"自定义参数"。 |
| `/T [<path>]`（临时目录） | 只有"数据装不下内存、要落临时文件"时才起作用；默认用系统临时目录已经最好。 |
| `/L <locale>` 的非 `C` 取值 | 官方 Remarks 明说"只有 C 是默认 locale 之外的唯一选择"，本机实测 `zh-CN` 也被拒（`无效的区域设置。`）。所以只把 `C` 做成一个固定 flag，**不提供自由输入框** —— 免得用户填一个必然失败的值。 |
| `progress.pattern` | sort 不输出百分比，且它是一次性算完再吐结果。**不凭印象编正则**（R1）。 |
| `nextSteps` / `quickActions` | "排完序之后该干什么"无法从输出里判断（输出就是一列排好的文本，没有任何可判定的标志）。按规范 §2.2 第 2 条，**不写**好过写一个 0 命中的正则。 |
| `danger` / `confirmText` | 没有任何动作会改数据；`fc`/`sort` 都只读输入文件。 |
| `execution: info` / `terminal` | 没有会弹窗或需要交互的动作（`/?` 也只是打印文本）。 |
| `requiresAdmin` | **不需要**，且是实测的（§2）。所以包级写 `false`，动作级不写。 |

## 7. 与同批 `fc` 包的关系（避免重复，也避免误抄）

`fc` 与 `sort` 是同一批做的两个 Windows 自带命令包（`sort.exe` 与 `fc.exe` 的文件版本
都是 `10.0.26100.8875`），下面这些结论**两边都成立、但必须各自实测**：

| 事实 | sort | fc |
|---|---|---|
| 输出编码（**宿主形态：无控制台**） | **oem / GBK 936**（§4） | **oem / GBK 936**（`plugins/fc/NOTES.md` §4） |
| 无控制台时语言 | **中文**（2196 B 中文帮助） | **中文**（906 B 中文帮助） |
| 有控制台时语言 | **英文**（3683 B 全 ASCII 帮助；管道里仍是中文） | **英文**（1173 B 全 ASCII 帮助） |
| 状态写 stdout | 结果与 `/?` 都在 stdout | 比较结果与 `/?` 都在 stdout |
| 状态写 stderr | 错误与警告在 stderr | 错误在 stderr |
| `/ ?` 退出码 | **0** | **-1（0xFFFFFFFF）** |
| 是否需要管理员 | 否 | 否 |
| 版本开关 | 没有（用 `/?`） | 没有（用 `/?`） |

**不要互抄**：`/?` 的退出码（0 vs -1）、能不能用通配符、输入是不是必填，
这三个问题的答案两个包各不相同；语言切换的条件也要各自看清（见 §4.1 的第三行）。
