# ADR 0001 — 宿主程序采用 .NET 10 + WinUI 3

- 状态：已接受
- 日期：2026-09-27
- 决策者：项目所有者

## 背景

需要一个 Windows 桌面程序，可视化地调用本机已安装的命令行软件。核心能力是：
子进程管理（启动、流式读输出、进度解析、取消时杀掉整棵进程树）、
由声明式清单动态生成的表单界面、进程树的作业对象控制、以及 Windows 原生体验。

## 决策

采用 **.NET 10 + WinUI 3（Windows App SDK 2.5.1，C#）**，以 **unpackaged** 方式部署。

## 理由

1. **进程管理最顺**：`CreateProcess`、ConPTY、Job Object 都是 Win32 API，C# 通过 P/Invoke 直接用，
   不需要为了拿到底层能力而引入 native 层。
2. **界面靠文档驱动**：WinUI 3 的数据绑定与控件模板足以支撑"清单 → 表单"的动态生成，
   而且能做出原生的 Fluent 观感。
3. **无运行时依赖的分发**：unpackaged + self-contained 时不需要用户预装 Windows App SDK 运行时，
   也不需要 MSIX 证书（个人自用场景下证书是纯负担）。
4. **环境已就绪**：VS 2026 Community 的 "WinUI 应用程序开发" 工作负载已装，Windows SDK 10.0.26100、
   .NET SDK 10.0.401 均到位。

## 后果

- **CI 可行**：已验证 `dotnet build` 在不启动 Visual Studio 的情况下能编译 WinUI 3 项目
  （0 警告 0 错误，24 秒），所以 GitHub Actions 的 `windows-latest` 可以承担构建与校验。
- **不装 C++ 工作负载**：纯 C# 路线用不到 MSVC，省下数 GB。
- **用户界面无法自动化验证**：WinUI 的界面呈现需要人眼确认，因此验收要靠"运行 + 截图反馈"的节奏。
- 需要 Windows 10 1809+（`TargetPlatformMinVersion 10.0.17763.0`）。

## 验证方式（已执行）

冒烟项目 `spike/winui3-smoke`：

| 检查 | 结果 |
|---|---|
| `dotnet build`（无 VS） | 通过，0 警告 0 错误，24 秒 |
| 实际启动 | 窗口真实弹出（标题 `WinUI 3 smoke test`），进程稳定存活 |

## 曾考虑并放弃的方案

| 方案 | 放弃原因 |
|---|---|
| Electron + TypeScript | `node-pty` 生态最成熟、UI 迭代最快，但包体约 150 MB、内存占用高，且为个人长期使用的工具引入一整个 Chromium 获益有限 |
| Tauri 2（Rust） | 体积最小、启动最快，但需要 rustup + MSVC，编译慢，Rust 侧开发摩擦大 |
| Python + PySide6 | 开发最快，但打包与进程边界体验最差，且 Python 3.14 生态偏新 |

## 附注：工作负载 id 的坑

VS 2026 里 "WinUI 应用程序开发" 的内部 id 是 `Microsoft.VisualStudio.Workload.Universal`——
看起来像 UWP，实为历史沿革（UWP 工作负载经两次改名演进而来）。
以后若用 `vswhere -requires` 检查，要写这个 id，别去找叫 WinUI 的 id（不存在）。
