# ADR 0002 — 执行引擎保留两条路径，伪控制台按工具包选择

- 状态：已接受
- 日期：2026-09-27
- 相关：`src/AllTool.Core/Execution/ProcessRunner.cs`、`ConPtyProcessRunner.cs`、规范里的 `runtime.usePseudoConsole`（见 `docs/spec/manifest-v1.md` §3）、陷阱 `P19`（`docs/ai/development.md`）

## 背景

宿主把子进程的标准输出读回来展示，并从中解析进度。最初的实现只有一条路径：**管道**（重定向 stdout/stderr）。

问题在一次真机实测里暴露出来：**7-Zip 只在真控制台里画进度**。

| 实测 | 结果 |
|---|---|
| `7z a` 把 stdout 重定向到文件（40 MB 输入） | 完整输出只有 354 字节，一个 `%` 都没有；加 `-bb1` 也只多出文件名 |
| 同一个操作接上伪控制台（ConPTY） | 输出里有 `0% / 8% / 18% …` 的百分比，进度条能走 |

这不是 7-Zip 的怪癖，而是**一类程序的普遍行为**：只在 `isatty` 为真时才画进度条（下载器、编译器、包管理器里都能见到）。
而"可视化命令行软件"这件事，如果连进度都看不到，价值就折了一半。

## 决策

**保留两条执行路径，由工具包在清单里按需选择**：

1. **管道路径（默认）**：`ProcessRunner.RunWithPipesAsync`。用 .NET 的 `Process`，输出干净、可直接当数据解析。
   取消用 `Kill(entireProcessTree: true)`。
2. **伪控制台路径（按工具包开启）**：`ConPtyProcessRunner`。自己调 `CreatePseudoConsole` + `CreateProcess`
   （.NET 的 `Process` 不支持挂到伪控制台上）。清单里写 `runtime.usePseudoConsole: true` 才启用。

配套的三个决定：

- **不做全局默认**。开伪控制台会让程序察觉"有终端"（可能强制彩色输出），输出里也会混入 ANSI 转义序列。
  v1 里只有明确需要的工具包（7zip）开启。
- **顺带把进程树语义做扎实**：伪控制台路径用 **Job Object**（`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`），
  并且 **挂起创建 → 加入 job → 恢复运行**——否则进程可能在入 job 之前就派生了子进程，那些孙进程取消时杀不掉。
- **界面侧负责清理**：展示前用 `AnsiText.Strip` 去掉转义序列；进度正则匹配前也先清理。

## 后果

- 7z 解压/压缩时界面进度条真的会走（实测 48 MB 样本走到 100）。这是这个工具"值得用"的关键之一。
- 多了一条需要长期维护的互操作代码路径（几百行 P/Invoke）。为此写了 `WindowsCommandLine`
  （CreateProcess 只接受一条命令行，引号规则必须正确）并配了 11 条单测。
- 工具包作者多了一个需要判断的开关。规范里写清了代价，避免"能开就都开"。

## 定位过程中最重要的那条知识

第一版 ConPTY 实现**拿不到任何输出**：管道里只有清屏与设置标题的转义序列，连原生 `whoami`/`7z` 都没有内容。

根因是：**子进程的标准句柄是从父进程复制过去的**——即使 `bInheritHandles = FALSE`，句柄"值"照样被填进
子进程的标准句柄槽；而 ConPTY 只负责提供控制台，**不会覆盖**这些继承来的句柄。于是：

| 父进程形态 | 子进程的输出去了哪 |
|---|---|
| 控制台程序 | 直接写到父进程的控制台（绕过 ConPTY） |
| stdout 被重定向（如 `dotnet test`） | 写到那个看不见的管道 |
| 无控制台的 GUI 程序（真实的 WinUI 宿主） | 没有可继承的句柄 → ConPTY 正常工作 |

修法：创建子进程时加 `STARTF_USESTDHANDLES`，把三个标准句柄显式置空。

**教训（比结论更值钱）**：它之所以难查，是因为"在测试宿主里失败、在真实宿主里其实能工作"。
当时的做法是先逐一排除 8 项假设，再造一个**独立 GUI 子系统探针**（`spike/conpty-probe`）复现出
"无控制台父进程下一切正常"，最后用 `GetFileType` 在子进程内部确认句柄类型，才锁定"继承"这一条。
**当"测试环境和真实环境不一致"时，先把环境差异本身当成假设来验证。**

## 曾考虑并放弃的方案

| 方案 | 放弃原因 |
|---|---|
| 只用伪控制台 | 所有工具的输出都会带上 ANSI 转义序列；机器可读的输出（如 `7z l -slt`、`scoop export`）会被终端渲染污染。管道路径对"把输出当数据"的场景明显更好 |
| 只用管道，放弃进度 | 等于承认"看不到进度"，而进度正是这类工具最需要可视化的部分 |
| 自己解析不依赖控制台的进度 | 对 7z 不可行（它压根不输出）；对每个工具单独写解析器也不现实 |
| 用 `.NET Process` + 某些开关骗过 `isatty` | 没有这样的开关；Windows 上判定的就是"标准句柄是不是控制台句柄" |
